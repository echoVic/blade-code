# Session Communication Style

Blade treats communication style as a durable configuration owned by the Session itself. It controls response tone and explanatory framework without changing model reasoning effort, Provider service tier, or native response verbosity. TUI, Web, ACP, and concurrent Sessions within the same process can use different styles; original choices are preserved after Runtime reconstruction, task retry, fork, and subagent inheritance.

## Selection and Semantics

Public selection values are:

```text
auto
pragmatic
friendly
explanatory
user:<name>
project:<name>
plugin:<plugin>:<name>
```

- `auto`: does not append a style section, preserves Blade default communication rules;
- `pragmatic`: direct, fact-oriented, concise, and action-emphatic;
- `friendly`: warm and collaborative while remaining fact- and task-oriented;
- `explanatory`: briefly explains codebase-specific implementation choices and engineering tradeoffs.
- namespaced custom styles: resolved from trusted user, project, or active plugin catalog.

`communicationStyle` is orthogonal to `responseVerbosity`. The former affects expression manner; the latter affects output density through model-native parameters. For example, you can simultaneously select `pragmatic + high` or `explanatory + low`.

Custom styles only accept catalog IDs, not arbitrary file paths, JSON, or prompt text. See [Trusted Custom Output Styles](/en/reference/trusted-output-styles.md) for source directories, Workspace Trust, budgets, provenance, and Session snapshot contracts.

## Prompt Boundary

Explicit styles add an independent section after default or Plan prompts and before trusted project instructions:

```text
<communication_style>
...
</communication_style>
```

The section explicitly controls only tone and explanatory framework, and cannot modify:

- Task scope and completion conditions;
- Safety and permission rules;
- Tool behavior and approval;
- Instruction source priority.

More specific user presentation requirements can override the expression manner for the current response. `auto` does not generate this section.

## TUI

```text
/style
/style auto
/style pragmatic
/style friendly
/style explanatory
/style project:review:strict
/personality friendly
```

`/personality` is an alias for `/style`. Without arguments shows selected and effective values; switching is not allowed during active turns. The status bar shows states such as `Style pragmatic` for non-`auto` selections.

## Web

Task Home and Session Composer provide custom Popover alongside inference controls. Both task dispatch and message requests send the same `communicationStyle`:

```json
{
  "modelId": "gpt",
  "reasoningEffort": "high",
  "serviceTier": "standard",
  "responseVerbosity": "high",
  "communicationStyle": "explanatory"
}
```

`session.updated`, catalog restoration, and fresh page load all restore selection from durable Session metadata. Web only receives security digests for custom styles, not prompts or host paths. Controls are locked during active turns to prevent current requests using half-old and half-new configuration.

## ACP

ACP Session setup exposes a standard select config option:

```text
id: communication_style
category: model
```

Clients switch via `session/set_config_option`. Options are dynamically generated by Session catalog and returned together with current values, model, `reasoning_effort`, `service_tier`, `response_verbosity` without requiring Blade-private extensions.

## Atomic Persistence

Model, reasoning effort, service tier, response verbosity, and communication style form the same Session settings group:

1. First validate all requested values;
2. Atomically replace Provider service when needed;
3. Update Runtime style selection;
4. Persist all changes in one `session_updated`;
5. Publish one `session.updated`.

Switching communication style alone does not reconstruct Provider. If durable writing fails, Blade restores the previous quintuple settings; if Provider initialization fails, both old service and old style remain usable.

Tasks, Teams, background/resume, retry, fork, and direct subagent resume all inherit the parent Session's communication style. Child Sessions own their own durable selection and can switch independently afterward.

Custom selections additionally persist the prompt SHA-256. On Runtime reconstruction, missing IDs or digest drift fail closed before model requests; explicitly switching to a built-in style clears old provenance.

## Production Qualification

Deterministic tests must cover complete vocabulary, prompt section order and permission guards, `auto` no-injection, Runtime switching without Provider reconstruction, active-turn rejection, JSONL create/update/fork, metadata failure compensating rollback, Task/Team/background/resume inheritance, TUI slash/status, Web Popover/SSE projection, and ACP config option.

Real GPT qualification completes two rounds of requests through a local transparent proxy that does not record Authorization. The first round must use `pragmatic`; after destroying Runtime restored from durable metadata to `explanatory` for the second round; the proxy must directly observe the corresponding section and permission guard in actual `system` or `developer` messages.

Production Web GUI must complete the first `pragmatic` round from Task Home, then switch to `explanatory` from Session Composer for subsequent turns; fresh load must restore complete messages and `explanatory`. Both upstream responses must be `200 text/event-stream`, JSONL, request body, and UI must be three-way consistent, and evidence files must not contain API keys.
